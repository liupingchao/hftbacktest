# 工作流接入指南

当下一个项目要沿用这套工作流时，使用这份指南完成接入。

目标是让新项目用尽量低的成本接入相同的 Agent 协作架构。

## 1. 推荐复制的文档包

把下面这些文件直接复制到新项目里：

- `workflow-manual.md`
- `task-dispatch-template.md`
- `thread-report-template.md`
- `qa-acceptance-template.md`
- `workflow-adoption-guide.md`

同时建议在新项目中创建：

- `AGENTS.md`
- `task_plan.md`
- `progress.md`
- `findings.md`
- `docs/thread-playbook.md`
- `docs/qa-acceptance-report.md`

## 2. 第一次接入前要先定义的内容

在第一个真实任务开始前，先定义这几件事：

1. 谁是总控？
2. 有哪些业务线程？
3. 是否有独立测试线程？
4. 是否有独立 QA 验收线程？
5. 哪份文件是固定 QA 文档？
6. 谁维护 `task_plan.md`、`progress.md`、`findings.md`？
7. 任务 ID 用什么格式？

推荐默认值：

- 任务 ID：`MMDDTxxx`
- 默认主链路：`业务线程 -> QA验收线程 -> 总控`
- 默认派发格式：Markdown 代码块
- 默认回报格式：Markdown 代码块
- 默认任务状态：固定 7 个状态

## 3. 新项目最小启动步骤

项目启动时，总控应先建立：

- 角色边界
- 线程归属规则
- 任务状态规则
- QA 文档路径
- 派发模板和回报模板

建议先初始化：

- `task_plan.md`
  - 写线程边界
  - 写当前任务池
- `progress.md`
  - 写当前重点和阻塞
- `findings.md`
  - 写风险和已知坑

## 4. 第一个任务怎么开始

1. 用户把需求交给总控
2. 总控先收口范围和验收标准
3. 总控选定正确线程
4. 总控用 `task-dispatch-template.md` 派发第一条任务
5. 执行线程用 `thread-report-template.md` 回报
6. QA 用 `qa-acceptance-template.md` 验收
7. 总控根据 QA 结果决定下一条任务

## 5. 哪些内容可以按项目调整

这些内容可以因项目而变：

- 真实线程名称
- 模块归属
- 文件路径
- 业务验收标准
- 环境相关发布或验证步骤

这些内容建议尽量保持稳定：

- 固定任务状态
- 任务 ID 格式
- 派发必须是 Markdown 代码块
- 回报必须是 Markdown 代码块
- 回报必须带 `是否进行QA验收`
- QA 文档作为最终验收事实源
- 默认一次只派发 1 个任务

## 6. 规则更新怎么推广

当工作流规则更新时，固定做法是：

1. 先更新规则文档
2. 不要在同一回合顺手触发别的验收流程
3. 给每个活跃线程的下一条第一任务加一次规则更新提醒
4. 不活跃线程等它下一次收到任务时再提醒

推荐提醒文案：

```md
规则更新提醒：
- 请先阅读规则文档后再执行本任务。
```

## 7. 最常见的失败方式

重点防这几种错误：

- 派发任务时没有任务 ID
- 派发任务时没有线程归属
- 子线程回报没有 `是否进行QA验收`
- QA 结果没有写进固定 QA 文档
- 一次派发多个有依赖关系的任务
- 用测试线程结果替代 QA 最终验收
- 实现线程默默扩大任务范围

## 8. 推荐接入顺序

如果新项目是从 0 开始，建议按这个顺序接入：

1. 复制工作流文档包
2. 定义线程角色
3. 建立固定 QA 文档
4. 建立 `task_plan / progress / findings`
5. 跑通第一条完整任务链路
6. 再根据实际情况微调

## 9. 最后建议

这套工作流最有效的时候，通常具备这些特征：

- 总控不越界
- 任务边界足够窄
- 回报只讲事实
- QA 对正常任务保持最终裁决权
- 规则更新先写文档，再执行

如果项目开始变慢或变乱，优先检查的通常不是 Agent 本身，而是：

- 任务边界是不是糊了
- 一次派发是不是太多了
- QA 职责是不是不清了
- 回报是不是不按模板来了
