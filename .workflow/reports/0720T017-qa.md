## Findings

1. 严重：malformed `orderStatus.status` 会抛异常，未能 fail-closed。
   - `status=[]` 或 `{}` 在三个分类器的 set membership 检查中触发 `TypeError: unhashable type`：
     - `examples/hyperliquid/hyperliquid_maker_order_manager.py:241-253`
     - `examples/hyperliquid/hyperliquid_tiny_live_m2_fill_window.py:2326-2338`
     - `examples/hyperliquid/cross_exchange_t024_same_window_acceptance.py:1670-1682`
   - manager 分类发生在 query 调用的 `try/except` 之外，异常不会被记录为 `unknown` evidence：`hyperliquid_maker_order_manager.py:531-543`。
   - 实际 manager 探针在首次 oid query 后中断，`live_status` 停留在 `submitted,submitted` 且 blocker 为空。
   - 同步重封的 acceptance fixture 直接抛 `TypeError`，没有输出 blocked manifest。
   - 违反“malformed query evidence fails closed”和“unknown remains visible and blocking”。

2. 高：最终 `live_status` 没有根据 finalizer 的最终账户快照重建订单状态和暴露。
   - finalizer 在 `hyperliquid_tiny_live_m2_public_watcher.py:7925-7946` 再次读取 final open orders。
   - tracked order 检测和 blocker 更新发生于 `hyperliquid_tiny_live_m2_public_watcher.py:6475-6485`。
   - 最终状态写入仍使用旧 `task7_manager_cycle.manager`：`hyperliquid_tiny_live_m2_public_watcher.py:9123-9138`。
   - `/tmp` 反例中 proof 发现 `2` 个 tracked open orders、`proof_status=fail_closed`，但最终状态仍显示：
     - `owned_open_order_count=0`
     - `working exposure=0`
     - manager orders 没有恢复为 `unknown`
   - blocker 字符串虽然更新，但 operator 的订单和暴露事实与最终账户证据矛盾。

3. 中：`filled` query 的 operator 状态语义自相矛盾。
   - manager 将 query `filled` 直接变成 terminal：`hyperliquid_maker_order_manager.py:471-473`。
   - cycle 因没有 active order 而将 cancel confirmation 标记为 pass：`hyperliquid_tiny_live_m2_public_watcher.py:514-523`。
   - 完整离线探针最终显示 order states 为 `filled`，同时 `fill_state=no_fill`、`filled_qty_btc=0.0`。
   - downstream reconciliation 正确保留 blocker，未形成 acceptance fail-open；但 operator status 不能可靠表达“query claimed filled、raw fill proof仍缺失”。
