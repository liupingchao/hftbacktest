## Findings

1. **P1 - segment identity fail-closed 不完整。**
   - `cross_exchange_liquidity_response_episodes.py:339-343` 只核对 segment
     manifest 的 `segment_id` 和 `campaign_id`，没有核对 `profile_id`。
   - `cross_exchange_liquidity_response_episodes.py:372-378` 读取 timeline 时
     只核对 `segment_id`，没有核对行级 `campaign_id/profile_id`。
   - 独立 failure injection 将 segment manifest 的 `profile_id` 改为
     `wrong-profile`，同时合法刷新上游 manifest SHA；builder 仍返回
     `passes=true`，顶层 manifest 为 `skhynix`，episode 行却为
     `wrong-profile`。
   - 这违反任务要求的八段 identity 硬门禁，可能在顶层 provenance 看似
     合法时静默混入错误 profile 数据。

2. **P1 - segment manifest 未进入最终 input-stability/provenance 闭环。**
   - `cross_exchange_liquidity_response_episodes.py:326-365` 的 provenance
     只加入 R0/R1 manifest 和每段三个 consumed data files，没有加入八个
     `segment_event_store_manifest.json`。
   - `cross_exchange_liquidity_response_episodes.py:1244-1250` 的构建后
     rehash 只覆盖上述集合。
   - 独立 failure injection 在 segment processing 后修改 segment
     manifest；其 SHA 已不再等于 R0 descriptor 冻结值，但 builder 仍
     `passes=true`，最终 provenance 中也没有 `segment_manifest` role。
   - segment manifest 决定 boundary、identity 和 timeline path；遗漏它
     使业务报告声称的输入二次 rehash 不成立。

3. **P1 - R1 primary-response tolerance 没有 fail closed。**
   - `cross_exchange_liquidity_response_episodes.py:307-312` 只验证 accepted
     primary horizons 和 join clock，没有验证 R1
     `horizon_tolerance_ms`。
   - builder 在模块常量中固定 `1000/2000ms -> 250ms`，而不是验证该值
     与 R1 manifest 一致。
   - 独立 failure injection 将 R1 tolerance 改为 `999ms`；builder 仍
     `passes=true`，并在 T017 manifest 中发布 `250ms`。
   - 当前真实 R1 恰好也是 `250ms`，所以已发布八段产物没有数值偏差；
     但实现不能阻止上游契约漂移，违反“使用 R1 primary-response
     semantics”的硬边界。

4. **P2 - replacement 不是严格原子发布。**
   - `cross_exchange_liquidity_response_episodes.py:1160-1173` 先把现有
     output rename 到 backup，再把 tmp rename 到 output。
   - 两次 rename 之间 output path 不存在；并发读者可见空窗，进程若在
     两次调用之间被终止也只剩 backup。
   - 普通 Python exception 会回滚，现有测试覆盖了该路径；但没有覆盖
     reader-visible atomicity 或 abrupt process termination。
